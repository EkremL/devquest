## Locate the state after sign-in

A dispatch operator signs into a shift roster. Opening the next roster page sometimes returns her to sign-in. The browser received the session cookie and the password verifier recorded success. Before changing any timeout or cookie flag, ask where the authenticated state was saved and whether the next request can find it.

~~~passage
study-server-side-state
~~~
### Keep browser evidence separate from server state

HTTP requests are independent. A server-side session gives the application a way to associate multiple requests with state held by the server. An anonymous session can hold form or navigation data. Authentication can add a verified identity and its security context to a session, depending on the application configuration. The existence of a session, by itself, tells you nothing about who signed in. Servlet sessions are scoped to the web application, so cookie presence alone does not imply that another application can load the same state.

### Use an opaque lookup key

A session identifier is an opaque value generated by the session system. It should be unpredictable, contain no user information and point to a server record. The client presents it, so the application must treat an incoming value as untrusted until it resolves to a valid session. Possession of an active authenticated identifier can grant access in the ordinary session model. Protect the value as a credential. Keep it out of URLs, support tickets and diagnostic logs. Use unrelated diagnostic identifiers for cross-request traces.

### Follow Set-Cookie and Cookie on separate requests

This fictional production roster app stores a host-only cookie, so the response omits `Domain`. `ROSTER_SESSION` is an illustrative name. Servlet applications often use `JSESSIONID`, and actual names depend on configuration. The request returns the cookie pair. The server cannot infer its attributes from that pair, so inspect the original `Set-Cookie` and browser storage metadata when debugging delivery. No `Max-Age` or `Expires` is shown here. Browser handling of such cookies, including session restoration, is separate from server expiry.

~~~http
HTTP/1.1 200 OK
Set-Cookie: ROSTER_SESSION=<redacted>; Path=/; Secure; HttpOnly; SameSite=Lax

GET /roster HTTP/1.1
Host: roster.example.test
Cookie: ROSTER_SESSION=<redacted>
~~~

## Trace the session lifecycle

~~~passage
study-session-creation
~~~
### Decide when to create or upgrade a session

In a Servlet application, `request.getSession()` can create a session. A login page or a saved request can have legitimate pre-login state before any authenticated state exists. After evidence is verified, a session-enabled login mechanism associates the context with the repository. A custom Spring Security 7.1 login path must integrate the configured session authentication strategy and save its context through the configured `SecurityContextRepository` when it expects persistence. Setting `SecurityContextHolder` alone changes the current request's view and may leave the next request without authentication.

~~~passage
study-session-lookup
~~~
### Look up state without accidentally creating it

A Servlet lookup using `request.getSession(false)` returns an existing valid session for the request or `null`. It does not create one on a miss. In the illustrated Spring Security arrangement, `HttpSessionSecurityContextRepository` associates the context with the session and allows subsequent requests to restore it. Separate these observations: was a matching cookie sent, did the session exist, did it have authenticated context, and did authorization allow the action? A request can also use a different configured authentication mechanism, so a missing session does not by itself define the response for every endpoint.

study-session-expiration

### Apply both lifetime boundaries where policy requires them

Idle timeout limits inactivity. `HttpSession#setMaxInactiveInterval` configures the servlet interval in seconds between client accesses before invalidation. An absolute lifetime caps how long authentication can live even if the session stays busy. It requires independent policy and enforcement when the container only supplies an idle interval. A longer-lived browser cookie can still point to an expired record. Similarly, removing a browser cookie does not necessarily expire the server's state.

The Java 25 example models only the application lifetime decision. Inputs come from trusted server time and persisted timestamps. Authentication time and last activity are assumed valid and ordered, with a nondecreasing clock for this example. The application checks prior activity before recording the current request. A production system would rely on the configured repository and concurrency policy for lookup, timing, expiry and invalidation.

~~~java
import java.time.Duration;
import java.time.Instant;

public class SessionWindow {
    private static final Duration IDLE_LIMIT = Duration.ofMinutes(15);
    private static final Duration ABSOLUTE_LIMIT = Duration.ofHours(8);

    static boolean usable(Instant authenticatedAt, Instant lastActivity, Instant now) {
        return Duration.between(lastActivity, now).compareTo(IDLE_LIMIT) < 0
                && Duration.between(authenticatedAt, now).compareTo(ABSOLUTE_LIMIT) < 0;
    }
}
~~~

At exactly 15 minutes idle the example rejects the session. Regular activity a minute before the 8-hour boundary still cannot extend the absolute window. If the roster operator reports an unexpected redirect, compare trusted timing metadata with the documented policy. Avoid assuming that the cookie's existence or browser expiration establishes the server decision.

~~~passage
study-session-invalidation
~~~
### Make a previously valid record unusable

Calling `HttpSession.invalidate()` makes that container session invalid and unbinds its attributes. A shared-session implementation must make revocation visible to other serving nodes. A new clean session can legitimately exist immediately afterward, so verify that the old identifier and its authenticated context are no longer accepted. Invalidation cannot retroactively stop a request that already loaded the context. A system that requires tighter guarantees for sensitive in-flight operations needs a fresh policy decision at the operation boundary.

~~~passage
study-session-logout
~~~
### End authentication on the server and clean up the browser

Under ordinary Spring Security 7.1 web configuration, the built-in logout flow uses a CSRF-protected POST when CSRF protection is enabled. It invalidates the HTTP session, clears the current security context and clears the configured repository. Cookie cleanup can improve browser behavior and should match the cookie's name, scope and relevant attributes. Cookie cleanup alone leaves server-side state available until it expires or is invalidated. Verify that the next protected request requires fresh authentication. An open tab displaying an old page is not evidence that a new protected request succeeds. Track other active sessions or external identity-provider sessions separately if the product supports them.

## Follow the state across nodes

~~~passage
study-shared-session-storage
~~~
### Give serving nodes access to the same active record

If node A writes to its own memory, node B cannot find that record when a load balancer sends it the next request. Sticky routing can reduce node changes, but a restart or failover still loses process-local state. A shared repository such as a supported Spring Session Redis or JDBC setup can make the state available across nodes. Verify namespace and serialization compatibility, timeouts, access controls and deletion propagation. A store outage is distinct from a normal session miss. Withhold protected data when current authentication cannot be restored, and use bounded operational diagnostics that distinguish the conditions. Avoid silently falling back to independent node-local copies.

## Protect the session handle

~~~passage
study-session-fixation
~~~
### Change the identifier across the sign-in boundary

Session fixation is the risk of carrying an identifier known before sign-in into authenticated use. Rotate it after authentication establishes an identity. In Spring Security 7.1 on modern Servlet containers, the default session fixation strategy for an existing session uses `HttpServletRequest.changeSessionId()`. The session can retain its attributes while its identifier changes. If no session exists yet, an authenticated session can receive a fresh identifier when created. On a privilege change, review whether policy requires fresh verification or rotation. Rotation limits pre-login reuse. It does not revoke a currently exposed authenticated credential unless that credential is actually replaced or invalidated.

~~~passage
study-session-theft
~~~
### Treat loss of a live identifier as loss of a credential

Session theft concerns exposure of an already active identifier. It can happen through accidental logging or mishandled storage as well as through compromised clients or transport. Keep credential values out of support exports, protect transit and storage, and constrain session lifetime. If a live identifier is exposed, revoke the affected server-side state, remove the exposure, and require new authentication. Keep the incident audit trail free of the identifier. Use defenses appropriate to the application, including protection from script injection and authorization on each protected action.

~~~passage
study-cookie-attributes
~~~
### Configure scope, delivery and visibility separately

Start with host-only scope when a single host needs the cookie. Choose a path that fits its intended requests. Path influences delivery and does not isolate arbitrary applications from each other as a strong security boundary. Keep browser retention aligned with the product's policy, and enforce actual session lifetime on the server. Check the attributes on the browser-facing response after proxying and in each supported sign-in flow. In Spring Boot 4.1, the `server.servlet.session.cookie` properties are one configuration surface for servlet session cookies. Inspect the actual issuer if another component writes your cookie.

~~~passage
study-cookie-httponly
~~~
### Reduce script access with HttpOnly

`HttpOnly` limits access through script-facing cookie APIs such as `document.cookie`. A browser can still attach the cookie to a request issued by script. Fix script injection even when the cookie is unreadable by script. The flag also does not stop the application or gateway from logging a received cookie.

~~~passage
study-cookie-secure
~~~
### Restrict delivery with Secure

`Secure` limits cookie delivery to secure transport under browser rules. Use HTTPS throughout the production flow and check the actual response. Browser and development-host exceptions should not define production assumptions. `Secure` does not encrypt the value at rest, prevent a JavaScript read by itself, or govern a proxy's downstream hop after TLS termination.

~~~passage
study-cookie-samesite
~~~
### Match SameSite policy to the navigation flow

Site is not the same construct as origin. Modern browsers generally use the scheme and registrable domain to determine whether a context is same-site. `Strict` limits cookies to same-site contexts. An explicit `Lax` also allows certain cross-site top-level navigations using safe methods. An explicit `None` permits cross-site delivery when other requirements are met and requires `Secure` in modern browsers. Browser privacy settings can still block cross-site cookies. Confirm what a real sign-in redirect or embed needs before choosing. Keep framework CSRF protection for state-changing requests. SameSite is one layer, especially where a browser automatically attaches the incoming credential.

When diagnosing the next session issue, record separate yes/no observations for delivery, repository lookup, context restoration and authorization. Test the transitions around sign-in, logout and timeout. Keep cookie values and login data out of the trace. The next session contrasts this reusable server state with token-based designs.
